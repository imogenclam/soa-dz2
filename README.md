# Marketplace API

ДЗ 2 по СОА. Сервис маркетплейса на Go: товары, заказы, промокоды, регистрация и вход по JWT, три роли.

Делал contract-first: сначала написал `api/openapi.yaml`, потом сгенерировал из него код и уже под него писал хэндлеры.

## Как запустить

Нужен Docker.

```bash
docker compose up --build
```

Поднимется Postgres, потом Flyway накатит миграции и завершится, и только после этого стартует сервер на 8080. Если миграция упадёт, сервер не запустится.

Между созданиями заказа по умолчанию должна пройти минута. Чтобы на демонстрации не ждать, можно выключить:

```bash
ORDER_RATE_LIMIT_MINUTES=0 docker compose up --build
```

Посмотреть, что лежит в базе:

```bash
docker compose exec db psql -U marketplace -c "select * from orders"
```

## Кодогенерация

```bash
go generate ./...
```

Генерирую через oapi-codegen, он подключён в go.mod как tool, ставить отдельно не надо. На выходе `internal/api/api.gen.go`: структуры запросов и ответов, интерфейс сервера и роутинг на chi. Этот файл в .gitignore, Dockerfile генерирует его заново при каждой сборке.

DTO руками я не писал. Хэндлеры реализуют сгенерированный интерфейс `StrictServerInterface`, так что если в контракте поменять ответ, проект просто не соберётся, пока не поправишь код.

Цены в контракте `number` с `format: decimal`. Через `x-go-type` они превращаются в `decimal.Decimal`, а не в float64, иначе на копейках начинаются ошибки округления.

## Структура

```
api/openapi.yaml          контракт
db/migration/V1__init.sql миграция для Flyway
cmd/server/main.go        запуск, всё собирается тут
internal/api              сгенерированный код
internal/middleware       логи, проверка токена, валидация
internal/auth             JWT
internal/apperr           ошибки в формате из контракта
internal/handler          сами эндпоинты
```

Порядок обработки запроса: сначала логирование, потом проверка токена, потом валидация по openapi.yaml и уже хэндлер. Валидацию делает kin-openapi прямо по спецификации, поэтому ограничения вроде maxLength, minimum или pattern есть только в yaml, в Go-коде я их не дублировал. Если запрос не прошёл, в ответе VALIDATION_ERROR и в details список полей с ошибками.

Бизнес-ошибки хэндлеры возвращают как `apperr.Error` с кодом, а дальше одна функция пишет их в ответ по схеме Error из контракта.

## Заказы

Это самая большая часть. Создание, изменение и отмена заказа целиком идут в одной транзакции, проверки делаю в том же порядке, что в задании.

Отдельно пришлось думать про одновременные запросы. Если пользователь отправит два POST /orders одновременно, оба могут пройти проверку «нет активного заказа» и создать два заказа. Поэтому в начале транзакции беру `pg_advisory_xact_lock` по id пользователя, и второй запрос ждёт, пока закончится первый. Товары блокирую через `SELECT ... FOR UPDATE`, чтобы два разных заказа не списали один и тот же остаток, а сортирую их по id, чтобы транзакции не заблокировали друг друга. Плюс в базе есть частичный уникальный индекс: активный заказ у пользователя может быть только один. Проверял пятью параллельными запросами, создался один заказ, остальные получили ORDER_HAS_ACTIVE.

Какие переходы статусов разрешены, написано в `orders.go` в виде таблицы. Отменить можно только CREATED и PAYMENT_PENDING.

Про скидку в задании написано, что процент не больше 70%, «в ином случае цена 100%». Я понял это так: если скидка получается больше 70% суммы, она не применяется вообще. Фиксированная скидка не может быть больше суммы заказа. При изменении заказа промокод проверяется заново, и если сумма стала меньше минимальной, скидка снимается, а использование промокода возвращается.

Если чужой заказ меняет админ, лимит частоты и запись в user_operations идут на владельца заказа, а не на админа.

## Авторизация

Access токен на 15 минут, refresh на 7 дней. В токене есть поле `typ`, поэтому refresh нельзя подсунуть вместо access и наоборот. При refresh роль заново берётся из базы.

Роль можно указать при регистрации, по умолчанию USER. Сделал так, чтобы было удобно показать все три роли. В реальном сервисе так, конечно, нельзя, любой зарегистрировался бы админом.

## Логи

На каждый запрос одна строка JSON: request_id, method, endpoint, status_code, duration_ms, user_id, timestamp. Для POST, PUT и DELETE ещё тело запроса, пароли и токены в нём заменяются на `***`. request_id возвращается клиенту в заголовке X-Request-Id.

## Примеры запросов

```bash
B=http://localhost:8080
curl -s -X POST $B/auth/register -H 'Content-Type: application/json' -d '{"email":"s@t.ru","password":"password1","role":"SELLER"}'
curl -s -X POST $B/auth/login -H 'Content-Type: application/json' -d '{"email":"s@t.ru","password":"password1"}'
# access_token из ответа подставить в T
curl -s -X POST $B/products -H "Authorization: Bearer $T" -H 'Content-Type: application/json' -d '{"name":"Mouse","price":20,"stock":100,"category":"tech","status":"ACTIVE"}'
curl -s "$B/products?category=tech&page=0&size=20" -H "Authorization: Bearer $T"
```
